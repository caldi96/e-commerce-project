# 🛒 대규모 트래픽 처리 이커머스 시스템

> 대규모 동시 요청을 고려한 고가용성 이커머스 백엔드 시스템

 ## 💡핵심 성과 요약

 - 상품 목록 조회 성능 **76.6배** 개선 (2,606ms → 34ms)
 - Redis + Kafka 기반 비동기 처리로 초당 **3,336건** 처리
 - Lua Script 기반 원자적 재고 관리로 **동시성 제어 및 정합성 보장**
 - Saga 패턴 적용으로 분산 트랜잭션 안정성 확보

 ## 📌 프로젝트 개요

 ### 배경
전자정부 프레임워크 기반 레거시 환경에서의 경험을 바탕으로,
실제 서비스 수준의 동시성 제어와 비동기 처리를 직접 설계하고 검증해 보고자 이 프로젝트를 시작했습니다.

 ### 개발 기간
 - 기간: 2025.11.03 - 2025.12.26 (8주)
 - 1인 프로젝트

 ### 기술 스택
 - **Language & Framework**: Java 17, Spring Boot 3.5, Spring Data JPA
 - **Database & Cache**: MySQL 8.0, Flyway, Redis, Caffeine Cache (로컬 캐시)
 - **Message Queue**: Apache Kafka
 - **DevOps**: Docker Compose
 - **Test**: JUnit5
 - **Performance Testing**: JMeter, k6
 - **Monitoring**: InfluxDB, Grafana

 ### 아키텍처
 [Client] → [Spring Boot API Server] → [Redis] (재고/쿠폰 원자적 처리) → [Kafka] (비동기 이벤트 발행) → [MySQL] (최종 데이터 저장)

 ## 🎯 주요 기능 구현

 ### 1. 선착순 쿠폰 발급
 **[문제 정의]**
 - 동시에 많은 유저가 쿠폰 발급 시 재고 초과 발생
 - 동시 다발적 DB 쓰기 작업으로 인한 성능 저하

 **[해결 방안]**
 - Redis Sorted Set + Lua Script 기반 원자적 쿠폰 발급 구현
 - Redis에서 쿠폰 발급 성공 시 유저에게 즉시 응답 후, DB 쓰기는 Kafka를 통한 비동기 처리
 - Saga 패턴 기반 이벤트 보상 트랜잭션 구현

 **[기술적 선택 이유]**
 - **Lua Script**: Redis에서 복합 연산을 원자적으로 수행하여 Race Condition 방지
 - **Sorted Set**: 타임스탬프 기반 발급 순서 관리 및 메타데이터 저장으로 확장성 확보
 - **Kafka**: 높은 처리량과 내구성으로 대량 이벤트 처리에 적합

 **[성과]**
 - 선착순 쿠폰 발급 시 재고 정합성 100% 일치
 - 선착순 쿠폰 요청 시 1ms 이내로 신속히 처리
 - Sorted Set에 메타데이터를 저장하여 추후 사용 이력 추적 및 분석 가능

 ### 2. 주문 시 재고 차감
 **[문제 정의]**
 - 동시 주문 시 재고 초과 판매 발생
 - 인기 상품의 경우 DB 접근 부하로 응답 속도 저하

 **[해결 방안]**
 - Redis String + Lua Script 기반 원자적 재고 차감
 - Redis 차감 성공 후 즉시 응답, DB 쓰기는 Kafka 비동기 처리
 - Saga 패턴 적용으로 실패 시 보상 트랜잭션 실행

 **[기술적 트레이드 오프]**
 - **선택**: Eventual Consistency (최종 일관성)
 - **이유**: 실시간 이커머스 특성상 3~5초 이상 지연 시 유저 이탈률이 급격히 증가(출처: The 3-Second Rule: Why 53% of Mobile Visitors Abandon Sites That Load Too Slowly)
 - **대응**: Dead Letter Queue + 재처리 메커니즘으로 정합성 보완

 **[성과]**
 - 동시성 문제 해결로 재고 오류 0건
 - 주문 요청 평균 응답 시간: 1ms 이내
 - Redis-DB 간 정합성 불일치 발생 시 DLQ를 통한 자동 재처리

 ### 3. 인기 상품 목록
 **[문제 정의]**
 - 실시간 인기 상품 목록 부재
 - 전체 상품 조회 후 정렬하는 방식은 성능상 불가능

 **[해결 방안]**
 - Redis Sorted Set을 활용한 일간/주간 인기 상품 TOP N 캐싱
 - 구매 및 조회 이벤트 발생 시 비동기로 점수 업데이트

 **[Key 설계 전략]**
 - 일별 인기 상품
   - 형식: ranking:daily:YYYYMMDD
   - 예시: ranking:daily:20251205
   - TTL: 7일

 - 주간 인기 상품
   - 형식: ranking:weekly:YYYY-W##
   - 예시: ranking:weekly:2025-W49
   - TTL: 28일

 **[Score 계산 전략]**
 - score = (판매량 * 10,000) + 조회수
 - 판매 1건 = 10,000점
 - 조회 1건 = 1점
 - **가중치 설정 근거**: 실제 구매가 발생한 상품이 더 높은 인기도를 가짐

 **[성과]**
 - 인기 상품 조회 시간: **O(log N)** 복잡도로 일정한 성능 보장
 - Redis Sorted Set의 ZREVRANGE 명령어로 TOP N 조회 최적화

 ### 4. Kafka 기반 비동기 주문 및 쿠폰 발급 처리

 **[문제 정의]**
 - 주문/쿠폰 발급 시 후속 RDBMS 쓰기 작업으로 인한 응답 지연
 - 비동기 처리 중 예외 발생 시 데이터 정합성 문제

 **[해결 방안]**
 - Redis 성공 후 Kafka Producer를 통해 이벤트 발행
 - Kafka Consumer가 DB 쓰기 작업 처리
 - 예외 발생 시 Dead Letter Queue로 전송 → RDBMS 메타데이터 테이블에 저장 → 수동 재처리

 **[성과]**
 - 비동기 처리로 응답 속도 향상 및 시스템 확장성 확보
 - DLQ를 통한 장애 추적 및 재처리 자동화

 ## 📊 성능 개선 결과

 ### 1. 상품 목록 첫 페이지 조회 최적화

 **[배경]**

 상품 목록 첫 페이지는 모든 유저가 가장 먼저 접근하는 페이지로, 조회 빈도가 매우 높아 DB 부하가 집중됨

 **[해결 방안]**
 **Redis 캐시**를 활용한 Look-Aside 패턴 적용

 **[부하 테스트 설정]**
 - 도구: JMeter
 - 동시 접속자: 10,000명
 - 테스트 시간: 30초간 초당 333명씩 증가
 - 각 사용자당 요청: 10회
 - 총 예상 요청 수: 100,000건

 **[개선 결과]**

| 지표 | Before | After | 개선율 |
|------|--------|-------|--------|
| 평균 응답 시간 | 2,606ms | 34ms | **76.6배** |
| 최대 응답 시간 | 4,392ms | 297ms | **14.8배** |
| 처리량 (RPS) | 1,446.8 | 3,336.2 | **2.31배** |

---

 ### 2. 카테고리 목록 조회 최적화

 **[배경]**

 카테고리 목록은 거의 변경되지 않으며 모든 유저에게 동일하게 노출되는 데이터

 **[해결 방안]**

 **Caffeine Cache (로컬 캐시)** 적용

 **[Caffeine 선택 이유]**
 - Redis 대비 네트워크 왕복 비용 제거로 더 빠른 조회
 - 분산 환경에서도 각 인스턴스가 독립적으로 캐시 보유 가능
 - 데이터 변경 빈도가 낮아 캐시 불일치 문제 최소화

 **[성과]**
 - 조회 시간: **1ms 이내** 안정적 유지
 - Redis 부하 감소로 리소스 절약

### 3. 선착순 쿠폰 발급 성능 테스트

**테스트 환경**
- 도구: k6 (Grafana Labs)
- 목표: 3,000명 동시 접속 시 정확히 100개 쿠폰만 발급되는지 검증
- 측정 대상: Redis Lua Script 기반 원자적 쿠폰 발급 로직

**테스트 시나리오**
1. 워밍업: Redis 메타데이터 캐싱 (실제 쿠폰 소진 없이)
2. 부하 증가: 1초 동안 3,000명까지 빠르게 증가
3. 피크 유지: 3초 동안 3,000명이 계속 요청 반복
4. 종료: 1초 동안 점진적 감소

**핵심 검증 사항**
- 동시성 제어: 3,000명이 동시에 요청해도 정확히 100개만 발급
- 중복 방지: 동일 사용자의 중복 발급 차단
- 응답 속도: 대규모 트래픽 환경에서도 일관된 응답 시간 유지

**테스트 결과**
- 총 요청 수: 28,711건
- 테스트 시간: 5.1초
- 처리량: 초당 **5,635건**
- 발급 성공: **정확히 100건**
- 발급 실패: 28,611건 (재고 소진 및 중복 발급)
- 시스템 오류: **0건** (에러율 0%)
- 평균 응답 시간: **433ms**
- 95% 응답 시간: **569ms**
- 최대 응답 시간: 601ms

**쿠폰 발급 성공률**
- 성공률: 0.35% (100/28,711)
- 실패율: 99.65% (정상적인 비즈니스 로직)

**주요 성과**
- 3,000명 동시 접속 환경에서 **정확히 100개만 발급** (오버 이슈 0건)
- 28,711건의 요청 중 **시스템 오류 0건** (100% 안정성)
- 초당 5,635건 처리로 **높은 처리량** 달성
- 평균 응답 시간 433ms로 **일관된 성능** 유지

**기술적 분석**

*동시성 제어 핵심 원리*

1. **Lua Script 원자성 보장**
   - Redis는 단일 스레드로 Lua Script를 실행하므로 스크립트 실행 중에는 다른 명령어가 끼어들 수 없음
   - 전체 검증 로직이 원자적으로 실행되어 Race Condition 원천 차단

2. **이중 검증 메커니즘**
   - ZCARD로 ZADD 전 수량 사전 체크 → 100개 이상이면 즉시 실패 반환
   - ZADD 후 ZRANK로 순위 재확인 → 이중 안전장치로 정확성 보장

3. **동시 요청 처리 흐름**
```
[요청 A] ZCARD(99) → 통과 → ZADD → ZRANK(99) → 성공
[요청 B] ZCARD(100) → 차단 → 즉시 실패
```
Redis 단일 스레드 특성상 요청 A가 완료될 때까지 요청 B는 대기하므로,
요청 B는 항상 최신 상태(100개)를 확인하여 정확히 차단됨

**시스템 안정성**
- Redis 워밍업을 통한 메타데이터 사전 캐싱으로 DB 병목 제거
- Kafka 비동기 처리로 DB 쓰기 부하 분산
- 실패한 요청도 정상적인 HTTP 응답 반환 (409 Conflict)
- Dead Letter Queue를 통한 예외 상황 추적 및 재처리 체계 구축
