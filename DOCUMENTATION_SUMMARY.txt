KEY FINDINGS
================================================================================

REQUEST/RESPONSE STRUCTURES:
- All requests: JSON (Content-Type: application/json)
- All responses: JSON
- Standard HTTP status codes (200, 201, 204, 400, 404, 409, 500)

VALIDATION RULES:
- NumericIDs: Long, Min 1
- Monetary Values: BigDecimal, Min 0
- Quantities: Integer, Min 1
- All major fields have @NotNull or @NotBlank annotations

DATA DEPENDENCIES:
- Categories can be created independently
- Products require valid categoryId (or null)
- Cart items require userId and productId
- Orders require userId and productId/cartIds
- Payments require orderId
- Coupons require comprehensive setup (dates, quantities, limits)

ASYNC PROCESSING:
- Orders: Created with PENDING status, processed asynchronously via Kafka
- Coupons: Issue operation uses Redis for atomic distribution, DB updated async
- Tests should account for these delays

AUTHENTICATION:
- NO authentication required (all endpoints public)
- NO @PreAuthorize, @Secured, or JWT annotations
- Development setup without security

INFRASTRUCTURE:
- Application: localhost:8083
- MySQL: localhost:3307
- Redis: localhost:6380
- Kafka: localhost:19093, 19094, 19095
- Consumer Group: ecommerce-consumer-group

CONNECTION POOLS:
- MySQL: max-active=10, max-idle=10
- Redis: max-active=10, max-idle=10, min-idle=2
- Bottleneck at high concurrency (100+ VUs)

================================================================================
SPECIAL FEATURES TESTED
================================================================================

1. PAGINATION
   - Products: page, size parameters
   - Orders: page, size parameters
   - Points: page, size parameters
   Tests should validate pagination boundaries

2. FILTERING & SORTING
   - Products: categoryId, sortType (LATEST, BEST_SELLER, MOST_VIEWED, etc.)
   Tests should exercise different sort combinations

3. FIRST-COME-FIRST-SERVED (Redis-backed)
   - Coupon issuance uses Redis for atomicity
   - Tests with high concurrency will trigger rate limiting (409 Conflict)
   - Expected behavior in stress tests

4. ASYNCHRONOUS PROCESSING (Kafka)
   - Order creation returns immediately with PENDING status
   - Actual order processing happens asynchronously
   - Tests should use sleep(2) after order creation

5. DATA RELATIONSHIPS
   - Products -> Categories
   - Orders -> Products, Coupons, Points
   - Payments -> Orders
   Tests must respect these dependencies

CRITICAL CONSIDERATIONS FOR K6 TESTING
================================================================================

1. TEST DATA PREPARATION
   - Create at least one product before running tests
   - Create test coupons for coupon tests
   - Tests generate unique userIds per VU (__VU + offset)

2. ASYNC HANDLING
   - Orders return PENDING immediately
   - Use sleep(2) after order creation
   - Account for eventual consistency in assertions

3. RACE CONDITION TESTING
   - Coupon issuance is rate-limited via Redis
   - High concurrency tests should expect 409 Conflict responses
   - This validates Redis atomicity

4. CONNECTION POOL LIMITS
   - MySQL/Redis pools max out at 10 concurrent connections
   - Tests with 100+ VUs may experience bottlenecks
   - Monitor pool saturation in test results

5. DATA ISOLATION
   - Each VU gets unique userId (__VU + offset)
   - Prevents conflicts in concurrent scenarios
   - Enables reproducible results

6. VALIDATION LOGIC
   - All endpoints validate request data
   - 400 errors expected for invalid input
   - Include validation error tests in suite
